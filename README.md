### 2.2 五条线程

```
readThread ─┬─> audioQ_ ─> audioDecodeThread ─> sampQ_ ─┐
            │                                            │
            │                              ┌─────────────┘
            │                              ▼
            │                    SDL 音频线程（pullAudio）
            │                       │            │
            │              swresample → S16 ──> 声卡
            │                       │
            │                       └── audClk_.set()  ← 主时钟
            │                                            │
            └─> videoQ_ ─> videoDecodeThread ─> pictQ_ ─┐│
                                                        ││
                                          ┌─────────────┘│
                                          ▼              │ get()
                              videoRefreshThread ◄───────┘
                                     │
                                帧回调 ──> QImage ──> 屏幕
```

### 2.3 数据形态的四次变化（音频）

```
① AVPacket（AAC 压缩包）
      ↓  audioDecodeThread（M6 的 Decoder）
② AVFrame（FLTP：32 位浮点、分平面）
      ↓  decodeOneAudioFrame（M9 的 swresample）
③ S16 交织 PCM（紧凑字节流，自有缓冲）
      ↓  pullAudio（M9）
④ 声卡缓冲
```

**每一次转换都有代价**——所以 M9 的目标格式选择原则是"**除了采样格式，其余尽量不动**"（采样率、声道布局都用源头的）。

### 主线 1：音视频同步的完整故事

**涉及文档：M5（数据结构）+ M9（产出端）+ M10（使用端）**

#### 起点：一个问题

> **声卡不会告诉你"此刻播到第几微秒"。**

SDL 的音频回调只知道"**我现在还需要多少字节**"——这是**未来需求**，不是**当前进度**。

#### 三步解决

**第一步（M5）：设计一个能"随系统时间推进"的时钟**

关键洞察：**两次帧到达之间，播放位置的变化量恰好等于流逝的系统时间**。

所以**不存"位置"这个会变的量，而存"位置与系统时间的偏差"这个在两次锚定之间恒定的量**：

```
clock     = pts_drift + now × speed
pts_drift = pts − t × speed        （锚定时算一次）
```

**配套的三个语义**：

| 语义 | 为什么需要 |
|---|---|
| **暂停冻结** | 否则暂停时进度条还在跑（M9 才补上） |
| **倍速外推** | 否则 2 倍速下时钟按 1 倍速走，画面越拖越晚 |
| **NaN 哨兵** | 表示"未锚定"，且 NaN 参与运算仍是 NaN——错误会传播而非被吞掉 |

**第二步（M9）：算出"现在播到哪了"**

```
播放头 = 帧结束PTS − (剩余未取走字节数 / 每秒消耗字节数)
```

**代入两端验证**：

| 状态 | remain | 播放头 |
|---|---|---|
| 刚解出一帧 | 整帧时长 | `PTS`（这一帧的起点）✓ |
| 帧取完时 | → 0 | `PTS + 帧时长`（这一帧的终点）✓ |

**中间线性插值**——平滑且单调，每次回调重算，**不累积漂移**。

**然后 `audClk_.set(播放头)` ——把时钟锚定进去。**

**第三步（M10）：视频问"到点了吗"**

```cpp
diff = 帧PTS − 主时钟
```

| diff | 处理 | 为什么 |
|---|---|---|
| `> 0` | **缩短睡眠**等 | 还没到显示时间 |
| `< -100ms` | **丢弃** | 硬显示会让后面的帧一起拖，越拖越远 |
| 其余 | **显示** | 到点了 |

**而 `> 0` 时缩短睡眠的那个动作（`remainingTime` 出参），让 10ms 从"固定节拍"变成"睡眠上限"** ——实测迟到量中位 **1.0ms**。

#### 如果只有视频（没有音频流）

**反过来用视频自己的 PTS 锚定同一个时钟**——两条路通向同一个 `audClk_`，**上层完全不用区分**。

#### 这条主线的关键数字

| 指标 | 数值 |
|---|---|
| 主时钟推进速率误差 | **0.2%**（1.500 秒墙钟 → 1.501 秒媒体时间） |
| 显示迟到量 | 最小 0.0ms / **中位 1.0ms** / 最大 27.0ms |
| 播完停在 | **5.024 秒**（素材 5.015 秒） |
| 倍速 1x/2x/0.5x | 推进速率 1.000 / 1.996 / 0.497 |

### 主线 2：serial 机制的完整故事

**涉及文档：M3（维护）+ M6（传递）+ M11（使用）**

#### 要解决什么问题

**seek 之后，队列里会混进"seek 之前的残留帧"。**

流程：

```
① seek → 队列 reset（清空 + serial+1 + 压 flush 标记）
② 解码器收到 flush 标记 → avcodec_flush_buffers() 清内部缓存
③ 但解码线程手里可能还攥着几帧旧数据
④ 它们会在 flush 之后才被 push 进帧队列 → 【混进了残留帧】
```

**后果**：用户会先看到几帧"跳回去"的旧画面、听到旧声音。

#### 三段接力

| 模块 | 做了什么 | 关键点 |
|---|---|---|
| **M3** | `PacketQueue` 维护 `serial_` | ★ **只有 flush 包才自增**，普通包**继承**当前值 |
| **M6** | `Decoder::decodeFrame` 把它存进 `pktSerial_` | 随包更新 |
| **M11** | `Frame::serial` + 渲染侧比较 | `if (frame.serial != queue.serial()) 丢弃` |

#### ★ 为什么"只有 flush 包自增"是关键

**这样"一次 seek 恰好对应一个序列号"**：

```
初始：serial = 0
start()  →  1     [flush@1]
包A 包B 包C  →  全是 1
用户 seek
reset()  →  2     [flush@2]
包D 包E      →  全是 2
```

**于是"比较 serial"就能精确判断新旧。**

**⚠️ 参考工程的 bug 是"每个包都自增"** ——那样队列的 serial 每来一个包就变，**"比较 serial"这个机制完全失效**。

#### 它跨了 8 个模块——这意味着什么

```
M3 铺第一段 → M6 铺第二段 → M11 用起来
        ↑ 中间隔着 M4 M5 M7 M8 M9 M10
```

**中间任何一段断了，机制就静默失效，而且【不报错】。**

> **这是"跨模块机制"最典型的例子：它的正确性只能靠端到端验证，单看某一层都看不出问题。**

#### 怎么验证

**用跨模块的不变量做断言**（而不是构造"残留帧"场景）：

> **"每一个被显示出来的帧，它的 `serial` 都必须等于队列当时的 `serial`"**
>
> **这个等式本身就是机制的定义。**

**实测：3 次 seek 期间显示 57 帧，serial 不匹配 0 帧。**

### 主线 3：三种队列的对比

**涉及文档：M3（两种）+ M4（一种）**

#### ★ 一条判据解释全部差异

> **队列里放的对象"是否持有需要转移的堆资源"，决定这个队列的复杂度。**

| 维度 | `PacketQueue` | `FrameQueue` | `MessageQueue` |
|---|---|---|---|
| **装什么** | `AVPacket`（**持堆内存**） | `AVFrame`（**持堆内存**） | 3 个 `int`（**纯值语义**） |
| **数据结构** | `deque` + `unique_ptr` 节点 | **定长环形缓冲** | `deque` |
| **容量** | 16MB / 8000 包 | **3 个槽**（音频 9） | **无界** |
| **背压** | ✅ **必须** | ✅（满即阻塞） | ❌ 不需要 |
| **serial** | ✅ | ❌（存在 `Frame` 里） | ❌ |
| **析构清理** | ✅ **必须 `unref`** | ✅（`av_frame_unref`） | ❌（连析构都不用写） |
| **行数** | ~200 | ~140 | **~100** |

#### 为什么容量差异这么大

**`FrameQueue` 只开 3 个槽**（视频）——三个理由：

1. **内存**：1080p 一帧 YUV 就 3MB，囤 100 帧 = 300MB；
2. **槽位复用**：`AVFrame` 对象可反复用，只有像素 buffer 需要换；
3. **背压**：3 个槽形成天然限制，**保证解码不会跑得远超显示**。

**而音频给 9 个槽**（帧小）——**两者在"时长"上量级接近（~120ms vs ~209ms），这才是真正的设计意图**：

> **队列容量的单位应该是"内存"或"时长"，而不是"个数"。**

#### ★ 三者的骨架是统一的

**尽管复杂度差很多，三者都保留了同一套 `start` / `abort` / `get` 骨架。**

> **一致性本身就是价值：读代码的人不用学第二套并发模型。**

#### 环形缓冲的一个通病

**不能用 `rindex == windex` 判断空/满**——绕圈之后这个等式在**两种情况都成立**。

**必须额外维护 `size_`。这是所有环形缓冲的通病。**

### 主线 4：生命周期与停机顺序（分五层）

**涉及文档：M3 / M6 / M8 / M9 / M12 / M13**

**这是全项目最容易出事的地方**——因为**顺序错的症状是"偶发卡死"或"偶发崩溃"，很难复现**。

#### 五层各自的停机顺序

| 层 | 在哪 | 顺序 | 错了会怎样 |
|---|---|---|---|
| **① 队列级** | M3 | `abort()`（置标志 + notify）+ `signal()`（叫醒另一端） | **只做一半 → 永久卡死** |
| **② 解码器级** | M6 | 先 `abort()` 再让对象析构 | **只 join 不 abort → 死等** |
| **③ 内核级** | M8/M9 | 置标志 → 关音频设备 → join 线程 → 停解码器 → 清资源 | 顺序错 → use-after-free |
| **④ 门面级** | M12 | `teardown()`：close → join 事件线程 → reset | **先析构后 join → 事件线程在已销毁的 cv 上醒来** |
| **⑤ 窗口级** | M13 | `closeEvent` 里先 `mp_->stop()` | **内核线程访问已析构控件** |

#### ★ 一个反复出现的"两步"模式

**M3 的 `abort` 是两步**：

```cpp
queue_->abort();          // ① 置标志位（让阻塞在 get() 的线程醒来）
frameQueue.signal();      // ② 叫醒睡在帧队列上的线程
```

**为什么必须两步？** 因为**同一个线程可能阻塞在两个不同的条件变量上**：

| 线程 | 可能阻塞在 | 谁负责唤醒 |
|---|---|---|
| 解码线程 | `pktq_->get()`（等包） | `PacketQueue::abort()` |
| 解码线程 | `fq.peekWritable()`（等空槽） | `FrameQueue::signal()` |
| 播放线程 | `fq.peekReadable()`（等数据） | `FrameQueue::signal()` |

**`abort()` 只是"把标志位设成 true"，它不会自动唤醒卡在【别的对象】的条件变量上的线程。**

> **这个机制在 M3 的实验台 [6] 被"分步验证"过**：
> **先只调 `abort` 并断言"线程还在睡"，再补 `signal` 并断言"被唤醒"**。
> **——把"这一步是必需的"从"我觉得"变成"测出来了"。**

#### ★ 两条贯穿性的原则

**原则一：对象生命周期的结束，必须晚于所有会用到它的线程生命周期的结束。**

**原则二：清理逻辑要封成幂等的函数。**

M12 的 `teardown()` 演示了这一点：

```cpp
play()  →  teardown() + 建新实例    // 重建
stop()  →  teardown() + 置 Idle     // 停止
```

**好处**：清理逻辑只有一份，**不会出现"play 里漏了一步、stop 里又对"的情况**。

### 主线 5：观察手段的三次演进

**涉及文档：M2 / M3 / M5 / M10 / M11**

**这一条主线讲的是"怎么让测试真的有效"** —— 它比任何单个模块的设计都更有普适性。

#### 演进过程

| 阶段 | 观察手段 | 什么时候失效 |
|---|---|---|
| **M3 初期** | **看队列存量** | 那时还没有消费者，**躺着的就是全部数据** |
| **M9 / M10 之后** | ❌ 存量**失效** → 改用**生产者侧计数器** | 流水线中间插入了消费者，**残留量随时序波动（实测 127 → 81）** |
| **M11** | **跨模块不变量** | ——（这类判据与时序无关，最稳） |

#### ★ 三次"观察手段"的具体案例

**案例一（M2）：怎么证明"资源真的被释放了"**

`AVFrame` 的释放是**静默的**，`printf` 看不出任何东西。

**做法**：找一个"会被释放这件事改变的、可观测的量"——**`AVBufferRef` 的引用计数**：

```
① frame 分配缓冲（计数 = 1）
② 自己再 av_buffer_ref 一份（计数 = 2）
③ 让 frame 出作用域 —— 真释放了就会还回一份，计数回到 1
④ av_buffer_is_writable() 判断是否唯一持有者
```

**判据**：出作用域后 `is_writable == true` → **确实释放**。

**案例二（M5）：怎么证明"漂移补偿有用"**

**做法**：**拿朴素做法当对照组**，用真实时间轴当基准。

```
单个帧间隔内实际流逝                  :  130.3 ms
朴素做法（直接用最近一帧 pts）最大误差  :  130.3 ms
漂移补偿（本类的 Clock）        最大误差:    0.000 ms
```

**而且测试 [7] 还构造了一个"错误实现"来复现跳变** ——**跳变 17.9 亿秒**（正是"多出来一个 `now`"的直接证据）。

**案例三（M10）：怎么量化"同步质量"**

**做法**：推导一个**只在目标达成时才变小**的量。

显示条件是 `diff = pts − master <= 0`，所以 `master >= pts` 恒成立——**`master − pts` 就是同步误差**。

**实测中位 1.0ms。**

> **为什么不用"帧率是否正确"？** 因为**"帧率对"不等于"同步对"**——
> 视频完全可以以 25fps 播放但整体滞后音频 500ms。

#### ★ 提炼出的通用原则

> **要验证一个目标，先想清楚"哪个量会随着目标达成而改变"。**
>
> 这个量可能**不是**你的代码直接产出的——`AVBufferRef` 的引用计数本来是为了内存管理，
> **但在这里被借用成了"释放与否的探针"**。

#### 类似的思路清单

| 要验证什么 | 可用什么量 |
|---|---|
| 资源释放 | 引用计数 / 句柄数 |
| 队列不丢数据 | **生产总数 == 消费总数**（不变量） |
| 锁已释放 | 再尝试加锁看会不会阻塞 |
| 线程已退出 | 线程数 / `joinable()` 状态 |
| 数据被拷走 | 改原缓冲区看副本变没变（M12 用过） |
| **机制生效** | **机制的定义式本身**（如 serial 的等式） |

### 主线 6：静默失败（最危险的一类 bug）

**涉及文档：M4 / M6 / M8 / M10**

#### ★ 共同特征

**不崩溃、不报错、不写日志——只是"某个功能没了"。**

**而"功能没了"太容易被归因为环境问题**（驱动、设备、配置）。

#### 四个案例

| 案例 | 现象 | 根因 | 为什么难查 |
|---|---|---|---|
| **M8** | **完全没声音** | `av_find_best_stream` 第 3/4 参数传反 | **"没声音"太像驱动问题** |
| **M8** | **包被全部丢弃** | 队列 `start()` 藏在 `Decoder` 里，解码器打不开就永不执行 | 没有错误提示 |
| **M4** | **界面永无反应** | 忘 `MessageQueue::start()` → 所有 `post` 被静默丢弃 | 不崩不报错 |
| **M10** | **UI 提前显示"播放结束"** | `Completed` 在"读完"时发而非"播完"时 | 状态迁移本身是"合法"的 |

#### ★ 唯一的解药

**让每一层都主动验证"数据到底流过没有"。**

**具体到工程实践，就是那些"看起来很笨"的断言**：

```cpp
// M8：如果只看队列存量，这个 bug 永远发现不了
check(d.audioPkts == ref.audioPkts, "音频包一个不多一个不少地分发完了");

// M9：如果设备没打开，这条会直接失败
check(info.targetSampleRate == 44100, "音频设备已按源采样率 44100 打开");

// M10：验证"没白跑"（内容非空）
check(rec.blankFrames == 0, "没有全黑的帧");

// M11：验证机制的定义式
check(mismatched == 0, "每一帧的 serial 都与队列一致");
```

> **它们把"静默失败"变成了一个刺眼的 `0`。**

#### ★ 一个相关的认知：测试可能依赖前面模块修掉的 bug

M9 的第一条断言是"**音频设备已按源采样率 44100 打开**"——**而它之所以能通过，依赖 M8 修掉的那个参数错位。**

> **如果跳过 M8 直接做 M9**，你会看到"设备没打开"，然后**去查音频代码——查错方向了**。
>
> **教训：测试失败时，先确认"它依赖的前置条件成立吗"，再看被测代码。**

## 六、★ 可复用的方法论（8 条）

**这一节是整套文档里"最不依赖这个项目"的部分**——它们可以带走。

### 方法 1：参照实现对照法

**用在**：说不清"是我封装的 bug 还是库的行为"时。

**做法**：**写一份绕开自己封装的裸 API 实现，跑同样流程**。

**案例（M6）**："125 个包只解出 124 帧"——

```
参照实现：喂完所有包后 123 帧 → flush 之后 124 帧
Decoder ：喂完所有包后 123 帧 → flush 之后 124 帧   ← 完全一致
```

**结论**：封装没引入差异，**124 vs 125 是 libavcodec 对这个文件的固有行为**。

**案例（M7）**：PCM 峰值比预期高 50% —— 裸 API 探针显示**原始解码数据峰值就是 0.4489（不是 0.3）**，而 `S16/浮点 = 1.0000`。

**结论**：`swr` 换算正确，是 **AAC 的 MDCT 过冲**。

> **没有这个方法，你会一直怀疑自己的代码；有了它，责任归属一目了然。**

### 方法 2：用"不变量"代替"场景构造"

**用在**：要验证一个"防止出错"的机制，但**构造出错场景很难**时。

**做法**：**断言"机制的定义式在任何时候都成立"**。

**案例（M11）**：serial 检查。

判据是 **"每一个被显示出来的帧，它的 `serial` 都必须等于队列当时的 `serial`"**——**这个等式本身就是机制的定义**。

**为什么不构造残留帧场景？** 那需要精确控制 seek 与解码线程的交错时机，**非常难构造且不稳定**。

> **不变量比场景更强：场景只能覆盖你想到的情况，不变量覆盖所有情况。**

### 方法 3：防御性机制有两面

**用在**：设计或验证"兜底逻辑"（丢帧、超时、补静音、丢弃过期数据）时。

**两面**：

| 面 | 要验证什么 |
|---|---|
| **该触发时触发** | 机制不是形同虚设 |
| **不该触发时不能触发** | 没有**误伤** |

**案例（M10 的丢帧逻辑）**：

- 测试 [6]：让回调故意变慢 → **丢帧 18 次**（该触发时触发）
- 测试 [1]：正常播放 → **已丢帧始终为 0**（不该触发时不触发）

**案例（M11 的 serial 检查）**：

- "不匹配数 == 0" + **"seek 之后画面仍在正常显示"**（没误伤）

> **误伤的后果往往比不触发更严重**（黑屏 vs 延迟一点）——**所以这一面必须测。**

### 方法 4：观察手段随架构演进

**用在**：测试写好了，但**改代码后测试变得不可靠**时。

**演进路径**：

| 阶段 | 手段 | 什么时候失效 |
|---|---|---|
| 初期 | **看中间队列的存量** | 一旦中间插入了消费者，存量就随时序波动 |
| 中期 | **在生产者侧计数** | ——（与时序无关） |
| 成熟 | **跨模块不变量** | ——（最强） |

**案例（M8）**：队列存量从 127 变成 81（因为 M9/M10 加了消费者）→ 改用 `readThread` 里的计数器。

**配套洞察**：**能让测试断言写得更精确的前提，是找到一个"不受其他模块干扰"的观察点。**

（所以"精确的 seek 落点校验"放到了 M9 的音频主时钟侧——那里不受消费影响。）

### 方法 5：边界条件代入验算

**用在**：写了一个公式时。

**做法**：**把公式代到它的两个极端，看结果对不对**。

**案例（M9）**：

```
播放头 = audioClock_ − remain
```

| 状态 | 用"帧起始 PTS" | 用"帧结束 PTS" |
|---|---|---|
| 刚解出一帧 | `PTS − 帧时长` ✗ | `PTS` ✓ |
| 帧取完时 | `PTS` ✗ | `PTS + 帧时长` ✓ |

**整整差一个音频帧（≈23ms）**——而**"看起来差不多"的直觉会放过它**。

> **教训：公式不能"看起来合理"就放过，要代入极端值验算。**

### 方法 6：诚实的边界标注

**用在**：留下"保险丝"、"死代码"、"防御性冗余"时。

**三类要标清的东西**：

| 类型 | 例子 | 怎么标 |
|---|---|---|
| **保险丝**（实际不触发） | M6 的 `send` EAGAIN 分支 | **说明"它不该触发，但如果触发说明 API 契约被破坏了"** |
| **死代码** | M3 的 `peekLast()` | **说明"它等价于 `peek()`，别按注释理解行为"** |
| **防御性冗余** | M12 的 `convertMtx_` | **说明"它当前不起作用，别以为加了锁就线程安全"** |

> **"看起来必要但实际多余"的代码，比"看起来多余但必要"的更危险**——
> 因为它会让人**放松警惕**，在真正需要的地方失去警觉。

### 方法 7：让"验证"本身变成一个功能

**用在**：设计接口时。

**案例**：

| 设计 | 目的 |
|---|---|
| M13 的 `openUrl(path)` + 命令行传参 | **可以不点任何按钮就把整条链路跑一遍** |
| M10 的 `videoonly` 素材生成参数 | **覆盖"纯视频降级"这条永远走不到的分支** |
| M5 暴露 `setAt(pts, time)` | **测试可以构造虚拟时间线，不依赖真实时间流逝** |

> **"让验证这件事变得容易"，本身就是一个值得投入的设计决定。**

### 方法 8：把"必须成对/按顺序做的事"收在一个函数里

**案例**：

| 函数 | 收拢了什么 |
|---|---|
| M8 的 `openComponent` | 开解码器 + 记元信息 + 启动队列（顺序不能乱） |
| M10 的 `videoRefresh` | 结束检测 + 各种判定（顺序即优先级） |
| M12 的 `setState` | 状态迁移 + 去重 + 日志（不会漏发信号） |
| M12 的 `teardown` | close → join → reset（三步顺序固定） |

> **好处**：**不会出现"某个调用点漏了一步"**。
